# 双语支持实施方案

更新日期：2026-09-22  
状态：代码实施与自动验证完成，等待手动验收；本文件是本次改动的唯一进度与验收依据。

## 1. 约束（先于实现）

1. 首发只支持英语（`en`）和简体中文（`zh_CN`）。新安装、导入旧状态或存储中没有 `language` 时，默认英语。
2. 语言由用户手动选择并保存到 `chrome.storage.local`。不按 IP、当前网页、浏览器或系统语言自动切换；Chrome 的 manifest locale 只负责扩展名称和商店元数据，不能覆盖用户的应用内选择。
3. 用户可见的静态和动态文字必须同一语言：options、onboarding、页面内命名层、右键菜单、按钮、提示、空状态、权限反馈、校验与导入错误均在范围内。不能留下“英文页 + 中文对话框”的混合状态。
4. 既有规则、名称和权限语义不可因添加语言字段而变化。旧状态读取必须兼容，未知语言值必须安全回退至 `en`。
5. 不增加联网、遥测或第三方运行时依赖；词典随扩展打包，离线可用。
6. 语言选择控件必须可键盘操作，并提供无障碍名称。切换后 options/onboarding 立即重绘；已打开的命名层在下次打开时采用新语言；右键菜单在安装、启动和语言变更时刷新。
7. 每一个翻译 key 必须由 TypeScript 和自动化测试覆盖。截图只能来自真实加载的构建产物；英文默认状态下的全球商店截图必须为英文。

相应架构决策见 [DECISIONS.md](DECISIONS.md) 的 ADR-007。

## 4. 实施顺序

1. 完成阶段 A，并给既有存储状态添加迁移测试。
2. 建立 `src/shared/i18n.ts`：应用词典使用稳定 message key；`_locales` 只保留 Chrome manifest 所需消息。领域层不返回面向用户的固定中文句子，界面以错误码和当前语言决定展示文本。
3. 将 options、onboarding、overlay 的静态标记改为带 key 的渲染，动态文本也只通过词典生成。语言选择器写入偏好后重新渲染当前页。
4. Background 在安装、启动、语言变更时重建右键菜单。应用服务读取保存的语言，确保错误响应可被调用端本地化。
5. 为两种语言分别断言关键按钮、模式、权限反馈、错误与右键标题；再完成类型检查、单测和生产构建。
6. 用构建后的 unpacked extension 在全新 profile 中采集英文全球截图。若提交中文本地化截图，另以 `zh_CN` 偏好采集，绝不复用中文截图到全球槽位。
7. 停在手动验收门，等待用户操作，不自行提交商店审核。
